What if the agent team were the output?

Most agent frameworks ask you to define a team first. SOAR asks whether the team can change as the task unfolds.

CARLOS GEORGESPROJECT NOTE · 2026

SOAR is a research prototype built around a goal and a resource budget. The root agent can break down work, spawn and retire child agents, allocate budget, and observe results. The agent graph is something the system produces while working, not something I have to specify up front.

I am interested in the interaction between three things that often get fixed ahead of time: team structure, available tools, and quality checks. In SOAR, a critic can identify a capability gap, the system can discover or synthesize a tool, and the next attempt can use a different organization.

Make the behavior observable

The runtime uses a small set of enforced interactions—spawn, delegate, observe, get a result, and kill. It keeps events and organizational memory in SQLite so I can inspect what happened, where budget went, and whether a different structure helped. I have also written design notes on observability, evaluation, and human escalation because those questions are as important as the agent loop itself.

If the system changes its own organization, the trace of those changes is part of the result.

Still a research question

The architecture and initial implementation are in place. The current work is experiments and GAIA-style evaluation. I do not yet have benchmark results that would justify a performance claim. For now, the project is a way to test whether adapting topology, tools, and evaluation together produces something better than fixing one of them at the start.

The code and design notes are in the public repository.
