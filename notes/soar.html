SOAR / AGENT SYSTEMS

Tracing failures in dynamic agent teams

How SOAR records delegation and tool use so I can tell where a run stopped.

Carlos GeorgesSeptember 25, 20263 min read

SOAR is a research prototype for agent teams that decide how to divide work while a task is running. A parent agent can create workers, assign tasks, inspect progress, collect results, and terminate a branch. The team structure can change during the run.

The runtime tracks resource use, evaluates outputs with critics, and can try to discover or build a missing tool. A failure can cause a retry, a change in capabilities, or an escalation to the parent.

When I ran evaluations, I found failures in the runtime itself that I needed to understand before judging the agents’ answers.

Workers failing before their first model call

During an exploratory GAIA benchmark run, the root created child agents that immediately failed. Their records showed failed tasks and no model spending. Some workers never made a model call.

The failure analysis traced this to exception handling. The provider wrapper handled a few expected errors, but other exceptions could reach a broad handler that recorded failure without enough detail. The final answer alone wouldn’t show that the worker failed before it started.

Search failed separately. A provider returned errors until the tool became unusable, and there was no effective automatic fallback. Some runs continued the research task without working search.

Event traces

SOAR records events when an agent spawns, a task is delegated, a tool fails, a critic rejects an answer, or a budget is reclaimed. The events go into SQLite and produce readable traces of model calls, tool use, and agent activity.

With the traces I can tell whether a worker started, whether it had the necessary tool, whether a critic rejected its answer, and whether the parent received a failure. Each case needs a different fix.

I also want health status to reflect observed behavior. A worker that keeps failing should show as degraded regardless of its own status report. The runtime needs to record cancellation and reclaim the budget for stopped work.

Small benchmark results

In one small Level 2 run, SOAR answered 11 of 15 questions correctly. The stored single-agent comparison passed eight exact-match checks; another answer had the correct substance but failed on spacing after a semicolon. The written summary counted that answer as correct. Both approaches failed all five Level 3 questions in the corresponding runs.

These are small runs. I can use them to investigate specific successes and failures, but I can’t draw a general performance claim from them. A stronger comparison would need consistent tools, scoring, resource limits, and repeated runs.

The critics also need evaluation. A citation check can find a missing reference without checking the cited claim, and a model judging another model can accept a confident mistake. SOAR is still a research prototype. The traces help me inspect its answers and failures in detail.

Sources: SOAR repository · GAIA failure analysis · Observability design.
