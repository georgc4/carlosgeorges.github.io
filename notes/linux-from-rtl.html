SYSTEMS / SEPTEMBER 2026

Getting Linux to /init on an SoC I designed

The interesting part of a full-system build is the handoff between layers. Every layer can be locally correct and the boot can still fail.

CARLOS GEORGESPROJECT NOTE · 2026

I wanted to build a RISC-V machine that did more than execute a small test program. The goal is an original RV32 SoC, small enough to target a Tiny Tapeout die, that can boot Linux from external NOR flash into PSRAM and give me a UART shell. There is also a small digit-classifier demo in the software image, because I wanted the machine to do something once it reached userspace.

Follow the boot, not just the core

The RTL includes an RV32IMA CPU, Sv32 memory translation, traps and supervisor state, timer and interrupt logic, SPI memory controllers, a boot ROM, and a UART. On the software side I built an M-mode SBI loader, a device tree, a Linux image, and a BusyBox initramfs. Each piece has its own tests, but the full boot makes the integration errors visible.

NOR flash→SBI loader→Linux kernel→BusyBox /init

A full-image Verilator run now moves the real image through modeled NOR and four PSRAM chips and reaches /init. BusyBox executes the init script and prints RV32 Linux userspace ready. The simulation stops at that marker; I have not counted an interactive shell prompt as proven yet.

The next constraint is physical

Reaching userspace in simulation is a milestone, but it does not mean the design fits on silicon. The first 8×2 SKY26d physical attempt failed during detailed placement after high area density and buffer insertion. The next work is reducing that pressure, finishing compliance and timing checks, and eventually validating a board. I like this project because there is nowhere to hide a bad assumption: if the hardware, firmware, kernel, and image disagree, the machine tells you immediately.

The repository has the RTL, boot flow, requirements trace, and verification plan.
