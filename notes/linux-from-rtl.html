RISC-V / DEBUGGING

Debugging a stuck Linux shell on my RV32 SoC

A CSR write latched a live interrupt bit and left the shell stuck. I fixed it and checked the result over UART.

Carlos GeorgesSeptember 25, 20263 min read

I’m building an RV32 SoC that boots Linux from external flash into external PSRAM. I’d eventually like to put it on a Tiny Tapeout chip and run a UART shell and a small digit-classification program. So far, the result is in RTL simulation: Linux boots, BusyBox ash accepts a UART command, and a separate RISC-V program runs.

Linux printed RV32 Linux userspace ready before the shell actually worked. I had to debug another interrupt problem to get from that message to an interactive prompt.

What’s in the SoC

The project includes the CPU, integer multiply/divide and atomic operations, privilege and trap handling, an Sv32 address-translation unit, serial memory controllers, a UART, a timer, and an interrupt controller. The software side includes the boot ROM, M-mode SBI firmware, device tree, Linux image, and BusyBox initramfs.

The full simulation starts from reset and transfers the image through a modeled NOR chip and four PSRAM chips. The serial-memory RTL drives the modeled pins, including the quad-lane transfers. Linux therefore exercises the memory protocol as well as the CPU and MMU. The accepted baseline needed a little over thirteen billion simulated core cycles to boot and run the acceptance program.

The interrupt loop

The first full acceptance run reached the userspace message and then got stuck in a UART/interrupt-controller loop. I added acknowledgement of the UART’s transmit-empty interrupt, but the next full run got stuck in the same place.

The remaining bug was in the CPU’s interrupt-pending CSRs. Reading mip or sip combines software-pending state with live interrupt inputs. My read/modify/write path used that combined value when updating the software state. If the external interrupt was high during the update, the write copied it into the software-pending register. The live interrupt could disappear while the copied bit stayed set.

The fix separates the software update from the live readback. A directed regression reproduces the latch on the previous RTL and passes with the correction. I then booted the full image again to check whether the shell worked.

Checking the shell over UART

The acceptance test now waits for the interactive ash prompt, sends /bin/acceptance_smoke as real UART RX frames, and waits for the program’s output. The UART has no RX FIFO, so the harness waits for Linux to consume each byte.

ASH> /bin/acceptance_smoke
ASH_PROGRAM_OK

The accepted run consumed all 22 command bytes and printed the result at cycle 13,010,943,367. The recorded result includes the RTL, simulator, and flash-image hashes. The test exercises receive interrupts, shell input, process execution, and output.

This is still a simulated machine. The physical-design runs haven’t produced a routed SoC, and I haven’t done full ISA compliance or board validation. The digit classifier hasn’t run on fabricated silicon. I’m using the shell-and-program test as an acceptance check while I work on area and boot time.
