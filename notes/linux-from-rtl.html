RISC-V / DEBUGGING

Linux printed “ready.” The shell still didn’t work.

A CSR write latched a live interrupt bit and left the shell stuck. I fixed it and checked the result over UART.

Carlos GeorgesSeptember 25, 20263 min read

I’m building an original RV32 SoC that boots Linux from external flash into external PSRAM. The eventual target is a Tiny Tapeout chip with a UART shell and a small digit-classification program. Right now, the useful result is in RTL simulation: Linux boots, BusyBox ash accepts a command over the UART, and a separate RISC-V program runs.

Getting to that last sentence took another round of debugging after Linux had already printed RV32 Linux userspace ready.

The machine underneath Linux

The project includes the CPU, integer multiply/divide and atomic operations, privilege and trap handling, an Sv32 address-translation unit, serial memory controllers, a UART, a timer, and an interrupt controller. The software side includes the boot ROM, M-mode SBI firmware, device tree, Linux image, and BusyBox initramfs.

The full simulation starts from reset and transfers the image through a modeled NOR chip and four PSRAM chips. The serial-memory RTL drives the modeled pins, including the quad-lane transfers. That means Linux exercises the memory protocol as well as the CPU and MMU. It also makes a boot expensive: the accepted baseline needed a little over thirteen billion simulated core cycles.

The interrupt that wouldn’t go away

The first longer acceptance run reached the userspace marker and then got stuck in a UART/interrupt-controller loop. I added proper acknowledgement of the UART’s transmit-empty interrupt. The next full run reproduced the loop.

The remaining bug was in the CPU’s interrupt-pending CSRs. Reading mip or sip combines software-pending state with live interrupt inputs. My read/modify/write path used that combined value when updating the software state. If the external interrupt was high during the update, the write copied it into the software-pending register. The live interrupt could disappear while the copied bit stayed set.

The fix separates the software update from the live readback. A directed regression reproduces the latch on the previous RTL and passes with the correction. Then came the longer check: boot the actual image again and use the shell.

Twenty-two bytes through the UART

The acceptance test now waits for the interactive ash prompt, sends /bin/acceptance_smoke as real UART RX frames, and waits for the program’s output. The UART has no RX FIFO, so the harness waits for Linux to consume each byte.

ASH> /bin/acceptance_smoke
ASH_PROGRAM_OK

The accepted run consumed all 22 command bytes and printed the result at cycle 13,010,943,367. The recorded result ties that run to the RTL, simulator, and flash-image hashes. That covers much more of the machine than stopping at an init message: receive interrupts, shell input, process execution, and output all have to work together.

There’s still plenty to do. This is a simulated machine, and the physical-design runs haven’t produced a routed SoC. Full ISA compliance, board validation, and the classifier running on fabricated silicon are also open. The shell-and-program result gives me a concrete acceptance gate while I work on the area and boot-time tradeoffs.
