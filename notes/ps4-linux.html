Giving a PS4 a second job

A game console is a surprisingly useful way to learn where Linux platform assumptions break.

CARLOS GEORGESPROJECT NOTE · 2026

I have been turning a PS4 into a Linux development platform. The attraction is the combination of capable hardware and awkward platform boundaries: a bootloader, kernel, GPU, root filesystem, network access, and recovery path all need to cooperate before the machine is actually useful.

Usable means recoverable

My work combines community bootloader and kernel code with a custom Buildroot userspace. I added support around kernel restart and AMDGPU recovery, including IOMMU handoff changes, so graphics and SSH could come back across repeated hardware restarts. An A/B root filesystem gives me a way to recover when an image experiment goes sideways.

I also put together a source-pinned cross-build and deployment flow for x86-64 images from an ARM64 host. The point is to make the machine a repeatable target for experiments, not a one-off boot screenshot. I have been packaging a CPU-targeted llama.cpp runtime and benchmark tooling to explore inference on this hardware. I do not yet have an accepted on-device inference result; userspace GPU compute is a separate validation task.

The hard part was not just getting Linux to start. It was making the next boot predictable.

Why I keep working on it

This is the same kind of end-to-end problem I enjoy at work, with fewer established paths. A failure can live in firmware handoff, kernel configuration, driver startup, filesystem state, or the image build. Tracing it across those boundaries is the project. The current platform is useful for experimentation; I am still working on making the inference setup and recovery flow more polished.
