SOAR started with a question: given a goal and a budget, could a group of agents decide how to organize its own work? The runtime lets a parent create workers, assign tasks, inspect progress, collect results, and terminate a branch. The structure develops as the task runs.

I wanted to explore that with actual execution. SOAR tracks resource use, evaluates outputs with critics, and can try to discover or build a missing tool. A failure can cause a retry, a change in capabilities, or an escalation to the parent.

That makes for an interesting architecture. It also creates a lot of ways for a run to fail before the architecture gets a fair test.

A worker can exist without doing any work

During an exploratory GAIA benchmark run, the root created child agents that immediately failed. Their records showed failed tasks and no model spending. The parent had assembled a team, but some of its workers never made a model call.

The failure analysis traced this to exception handling. The provider wrapper handled a few expected errors. Other exceptions could reach a broad handler that recorded failure without preserving enough information about what happened. Looking only at the final answer would have made this look like a reasoning failure.

Search had its own problem. A provider returned errors and the tool eventually became unusable. There was no effective automatic fallback. Some runs continued attempting a research task after losing the capability they needed to complete it.

Record the transitions

The useful unit of observation is each change in the run: an agent spawned, a task delegated, a tool failed, a critic rejected an answer, or a budget was reclaimed. SOAR records typed events in SQLite and produces readable traces of model calls, tool use, and agent activity.

This lets me ask more specific questions. Did the worker ever start? Did it have the necessary tool? Did it return an answer that the critic rejected? Did the parent receive the failure? Those cases need different fixes.

Health also has to come from observed behavior. A worker that keeps failing should become visibly degraded; its own description of how well it is doing is insufficient. Cancellation and budget reclamation matter for the same reason. The runtime has to account for the work it started.

Be careful with the score

In one small Level 2 run, SOAR answered 11 of 15 questions correctly. The stored single-agent comparison passed eight exact-match checks; another answer had the correct substance but failed on spacing after a semicolon. The written summary counted that answer as correct. Both approaches failed all five Level 3 questions in the corresponding runs.

That is enough evidence to investigate individual successes and failures. It is not enough to establish that the organizational approach is generally better. The comparison also needs consistent tools, scoring, resource limits, and repeated runs.

Critics have limits too. A citation check can find a missing reference without establishing that a cited claim is true. A model judging another model can accept confident mistakes. SOAR is a research prototype, and its evaluation needs scrutiny alongside its answers. The failure traces have been useful precisely because they make those questions concrete.
