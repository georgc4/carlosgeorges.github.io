I’m using a PS4 to run Linux and test GPU inference. I’ve worked on the boot path, userspace, recovery after failed updates, and the GPU problems that showed up during inference.

This builds on the community’s PS4 Linux and loader work. My contributions are in the build and deployment system, loader diagnostics, kernel handoff, recoverable root filesystems, and the path from an initialized GPU to an inference result.

Boot and recovery

I built a pinned cross-build environment that runs natively in ARM64 Linux containers and produces an x86-64 kernel and Buildroot userspace. Keeping the source, configuration, and output identities together makes it possible to tell which image is actually on the console.

One early boot problem came from allocating a large contiguous image. I extended the loader’s diagnostics and changed image staging to use smaller chunks. That got the kernel and userspace onto the hardware.

I added A/B root-image trials with checks for storage, networking, and SSH before a candidate becomes the accepted slot. Kernel handoff needed its own work: the PS4’s devices don’t automatically arrive in the state the next Linux kernel expects. The patches cover shutdown ordering, stale IOMMU translation, and GPU recovery. Repeated Linux-to-Linux transitions eventually returned with display initialization, GPU ring checks, and SSH working.

The A/B setup lets me try a new image and return to the previous one if it fails. The handoff and recovery checks also give me a known starting point for the GPU work.

GPU inference

I started with a CPU baseline using a pinned small model, deterministic output checks, and repeated measurements at several thread counts. Generation was slower at the highest thread count.

A successful GPU kernel self-test didn’t cover userspace compute or model execution. I found separate problems in compute, result transfer, and model operations. I worked through targeted cases, then compared intermediate model results between CPU and GPU.

That comparison narrowed a major error to a change in matrix-operation dispatch. A smaller numerical difference also mattered: CPU and GPU input arithmetic could change the final token ranking. The trial implementation uses narrower dispatches, a simpler attention path, and matching input rounding for the affected projection.

All 25 model layers now offload to Vulkan, and two short-prompt runs returned the exact expected output. The checksums and post-run hardware checks passed for those runs.

Longer prompts

A larger prompt caused a GPU fault during prefill, before any answer was generated. A recovery attempt didn’t restore the machine. The passing result is limited to the tested short prompt. Longer inputs and recovery still need work.

I want to get larger prompts working, check output across more inputs, and then measure performance with a configuration that survives those runs.
